# 開発フロー — キャラチャットアプリ（仮称）

- 版: 1.3（2026-11-23、最終版）
- 対象の設計書: 「設計書 — キャラチャットアプリ」版1.2
- 状態: **開発可能**（2026-11-23、設計書とともにレビュー確定。開発開始は利用者の合図による）
- 原則: 開発は本フローに沿って進める。各フェーズの完了条件を満たしてから次へ進む。問題が出たら、関係するフェーズへ戻る。
- 改訂履歴: 1.0 初版。1.1 レビュー1回目を反映（根幹検証の前倒し等）。1.2 レビュー2回目を反映。1.3 レビュー3回目で総評「開発可能」。残った中5件を文言修正で反映し、最終版とした。

## フェーズ0: レビューゲート（着手前）

1. 設計書と本フローを、連携済み Claude Code（独立プロセス）へ渡してレビューさせる。観点: 実現可能性、矛盾、不足している要件、過剰な仕様、リスク。
2. 指摘を受け取り、Muse 側で妥当性を判断して文書を修正する（採用しない指摘には理由を残す）。
3. 修正版を再度レビューさせる。再レビューの終了条件は「重大の未解決指摘がないこと」。軽微な修正だけの場合は再レビューを省略できる。
4. 双方で問題なしと確認できたら、両文書に「開発可能」とマークする。
5. 開発の開始は利用者の合図を待つ。合図があるまで着手しない。

完了条件: 両文書が「開発可能」マーク済みであること。

## フェーズ1: 根幹検証と土台

1. **根幹の一巡検証（最初に行う）**: 最小のスペースを用意し、次の1巡が実際に動くことを小さい実験で確かめる。
   - スペースのアクション経由で、リクエストの読み取りと返信の書き戻しができること。
   - 仲介を固定スクリプトで行えるか（スクリプトからアクションを呼べるか、認証方法を含む）。行えない場合は、エージェントが受け渡しのみを担う形に確定する。
   - 合図の自動検知（フック等の軽量監視）が成立するか。成立しない場合は「合図はチャットで連絡」方式に確定する。
   - 分離条件（設計書3章）で Claude Code を起動し、対象キャラの返信が1件得られること。ツール無効化が効いていること、認証の渡し方が成立すること、実際に渡る文脈（除去できない情報の範囲）も確認する。検証では仮キャラ1件を使う。
   - 検証結果は設計書へ反映する（想定済みの代替への切替は再レビュー不要。想定外の方式変更が必要になった場合はフェーズ0へ戻る）。
2. fullstack スペースの本構築: データモデル（設計書7章）を実装する。
3. 画面3種（キャラ選択／チャット／グループチャット）と基本アクション（キャラ・会話・グループの読み書き、返信リクエストの登録・状態遷移）を実装する。この段階では生成は繋がない（発言とリクエストが貯まるところまで）。

完了条件: 根幹検証の結果が設計書に反映され、画面からキャラ選択・発言・グループ作成ができ、データが保存されること。

## フェーズ2: キャラ初期取り込み

1. 冒頭で取得方法を確認する: アバターテンプレ管理アプリのアクション経由で全プロファイル（書き出しJSON＋画像）を取得できるか。できない場合は、1件ずつの書き出しJSONによる取り込みに切り替える。
2. 変換処理（JSON→設定文。配信ツールの変換仕様と同一。関係・呼び方は分離して保存する）を通し、アプリへ登録する。画像は実体を保存する。
3. 変換結果を数キャラ分目視確認する（関係・呼び方が分離パートに入っていること、画像が表示されること）。

完了条件: 全キャラが一覧に並び、設定文（分離済み）と画像が正しく入っていること。

## フェーズ3: 生成まわり

1. 生成手順を実装する: リクエスト取得 → 材料の組み立て（設計書3章）→ Claude Code 独立プロセスで生成 → 書き戻し（グループは分割処理を含む）→ リクエスト完了処理。返信の保存と完了更新は冪等に行う。
2. 異常系（設計書8章）を確認する: 失敗の記録と画面表示、利用枠到達の区別、生成プロセスの強制終了、processing のタイムアウト確定と復旧、遅延書き戻しが破棄されること、状態ごとのクリア・削除の可否、分割のフォールバック（前置き、名簿外の名前、表記揺れの崩れ例で原文が失われないこと）、二重生成の防止。
3. 混入・混同チェック（設計書9章）: 複数キャラでテスト生成し、Muse 本体のペルソナの混入と、グループでのキャラ間の口調混同がないか確認する。

完了条件: 合図→生成→表示の一連が動き、異常系と混入・混同チェックが済んでいること。

## フェーズ4: 検証

1. 設計書9章の受け入れ基準を1つずつ確認する。
2. スマートフォン実機での表示・操作を確認する（利用者にも確認してもらう）。

完了条件: 受け入れ基準を全て満たすこと。

## フェーズ5: 納品・運用

1. 使い方を案内する: 発言の仕方、合図の仕方、キャラのJSON追加手順、グループの作り方、画像差し替えの依頼方法。
2. 運用ルールと制限を案内する: 生成は合図制、利用枠（Pro）の消費は生成時と仲介分、履歴は直近20発言までしか生成に参照されない、会話ログの正本はアプリ内のみで外部バックアップは無い（アプリ削除でログも消える）。

完了条件: 利用者が使い始められる状態であること。

## 戻り先の目安

- 仕様の疑問・矛盾が見つかった → フェーズ0（設計書を直し、重大な変更なら再レビュー）。
- 根幹検証で想定外の方式変更が必要になった → フェーズ0。
- 変換の仕様の問題 → フェーズ2の中で調整する。変換仕様そのものを変える場合はフェーズ0。
- 生成の品質問題（混入・混同・分割の崩れ）→ フェーズ3（材料の組み立てと指示文を調整）。
- 画面・データの問題 → フェーズ1。
