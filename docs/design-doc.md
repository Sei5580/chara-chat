# 設計書 — キャラチャットアプリ（仮称）

- 版: 1.10（2026-11-24、カテゴリ分けチェックボックス：オンでフォルダ分け、オフでカテゴリを無視した全表示）
- 状態: **開発可能**（2026-11-23、Claude レビュー3回目で「重大の未解決指摘なし」を確認し確定。開発開始は利用者の合図による）
- 元になった物: 配信コメント返信ツール（わんコメ連携）の「個人チャット」部分のみを抜き出す。配信関連の機能は一切含めない。
- 改訂履歴: 1.0 初版。1.1 レビュー1回目の重大・中を反映。1.2 レビュー2回目の残存重大1件と中6件を反映。1.3 レビュー3回目で総評「開発可能」。残った中5件（ボタンと確定の主体、実行前の状態確定、履歴からの未返信発言の除外、分割のコロン完全一致、チャット合図と failed の関係）を文言修正で反映し、最終版とした。1.4 運用開始後の利用者要望による変更: (1) 発言と同時に自動で返信生成を開始し、「返信をもらう」ボタンは廃止。(2) 生成失敗時は、対象の利用者発言を入力欄へ下書きとして戻し、再送信できるようにする。(3) キャラ画像をアプリ内で変更可能にし、取り込み時にトリミングして保存する。背景: 実機でボタン押下してもリクエスト自体が作成されず返信が始まらない事象が確認されたため、リクエスト作成を発言保存と同一アクション内で行う方式に改める。1.5 レビュー機能を追加（4.4章）: 特定の返答への指摘を履歴に残し、AIがキャラ設定を見直してJSONで再出力し、差分を履歴に残したうえで**自動適用**する（利用者が自動適用を選択。履歴からの取り消し可）。なお1.4の自動開始は本番で発火しない事象が残ったため、2分間隔で signalall を呼ぶ定期実行（cron、space_action）を併設し、本番で発言→返信が通ることを確認済み。1.6 運用開始後の利用者要望による変更: (1) キャラ一覧の並び替え（五十音順・追加順・最近使用した順）を追加。(2) キャラ一覧の簡易表示（1行表示）を追加。(3) 不具合修正: トリミングのプレビューでドラッグ時に表示領域外の画像が描画されない問題と、会話を開いて一覧へ戻っても未読バッジが即時に消えない問題を直す（4.6章）。1.7 キャラ一覧の「画像を変更」ボタンを小さい「設定」ボタンへ置き換え、押すとメニュー（キャラ設定閲覧／画像変更／表示名変更）を開くようにする（4.7章）。1.8 運用開始後の利用者要望による一括修正5件（2026-11-25、4.8〜4.12章）: (1) 並び替えの即時反映。(2) チャット画面内の「新着」区切り表示（LINE風）。(3) グループチャット選択への並び替え適用。(4) キャラのカテゴリ分類。(5) チャット全文出力（コピーペースト用）。

## 1. 目的

スマートフォンから、好きなキャラクターと1対1の会話、および複数キャラクター同士の掛け合いを楽しむための専用アプリ（スペース）。配信とは無関係に、キャラクターとの会話そのものを楽しむことが目的。

## 2. 前提・実現方式

- 置き場所はスペース（fullstackアプリ）。データはアプリ内に保存される。スペースは公開せず、閲覧・操作は利用者本人のみとする。
- アプリ単体では文章生成ができない。返信の生成は、連携済みの Claude Code を独立プロセスで呼び出して行う。
- 実行場所: Claude Code、監視、仲介処理はいずれも Muse の環境（VM）上で動く。利用者のPCでは何も動かさない。Muse の環境が停止している間は合図を受けても処理されず、復帰後に処理される。
- 流れ:
  1. 利用者がアプリで発言すると、その発言はアプリ内に保存され、**発言の保存と同一アクションの中で返信リクエストが作成（既存の pending があれば upto_seq を進めて統合）され、直ちに生成が開始される**（未返信の判定規則は7章）。「返信をもらう」ボタンは置かない（1.4で廃止）。利用者は発言して返信を待つだけとする。
  2. チャットで Muse に合図する方式も残す。チャット合図は、全ての未返信の会話・グループを対象とし、リクエストが無いものには作成して処理する。ただし、最新のリクエストが failed で、その upto_seq より後に利用者の発言が無い対象は除外する（新しい発言があれば、failed 分も含めて対象とする）。processing 中の対象はスキップし、解散済みグループは対象に含めない。合図の処理中に10分超の processing を failed に確定した対象は、その回の処理対象には含めない（次の合図で処理できる）。
  3. 仲介処理が材料（キャラ設定文＋会話履歴）を組み立てて Claude Code へ渡し、返ってきた返信をアプリへ書き戻す。処理は1件ずつ直列に行う。
  4. 返信は即時ではない。発言から数分以内を目安とする。
  5. 生成が失敗（failed）になった場合、そのリクエストの対象だった利用者発言はログから取り除き、本文を対象ごとの「戻し下書き」として保持する。画面は下書きを入力欄に復元して表示し（失敗した旨の通知も出す）、利用者はそのまま、または直して再送信できる。再送信は通常の発言として扱われ、自動で生成が始まる。
- 仲介処理は固定スクリプトによる機械処理を第一とする（取得、材料の組み立て、生成の起動、分割、書き戻し）。スクリプトからスペースのアクションを呼べるか（認証方法を含む）が根幹検証の対象。呼べない場合は Muse（エージェント）が受け渡しのみを担い、材料の組み立てと分割はスクリプトで行う（エージェントは本文の要約・改変をしない）。
- 合図の自動検知（ボタンを押しただけで処理が始まる形）には、LLM を使わない軽量な監視（フック等）を使う想定。検知方法も根幹検証の対象とし、確定できない場合は「合図はチャットで連絡する」方式に確定させる（想定済みの代替への切替は再レビュー不要）。

### トークン消費の見積もり
- 待機中の監視は LLM を使わないため、トークンを消費しない（エージェントが定期的に起きる方式は採用しない。3分間隔で1日480回、何もなくても数百万トークン規模になりうるため）。
- 消費の中心は生成時: 1対1で入力数千トークン＋出力数百〜千トークン程度／回。グループは参加人数分の設定文が加わる。
- 仲介をエージェントが担う場合は、その読み書きの分も消費する（スクリプト化できた場合はほぼ生成分のみ）。実測して運用案内に反映する。
- 生成には Claude の利用枠（Pro、5時間・週の上限、他の利用と共有）を使う。

## 3. 生成方式（ペルソナ混入の防止）

- Muse 本体（現在設定中のキャラクターの人格で動いている）が直接返信文を書くと、話し方や一人称が混入する恐れがあるため、返信文は Muse 本体では書かない。
- Claude Code の起動条件（分離条件）:
  - 専用の CLAUDE_CONFIG_DIR を使う。中身は認証情報のみとし、利用者設定・メモリ・フック・スキル・MCP設定は持ち込まない。認証の渡し方（認証情報のみを置いた専用フォルダ／OAuthトークンの環境変数）はフェーズ1で確認して確定する。
  - 作業ディレクトリは空の専用フォルダとし、その上位フォルダにも CLAUDE.md 等の設定ファイルが無い場所に置く。システムプロンプトは対象キャラの材料で置き換える（渡し方はファイル指定とし、コマンド文字列に長文を埋め込まない）。会話材料（履歴＋対象の発言）は標準入力で渡す。
  - ツールは無効化して呼ぶ（`--tools ""` 相当）。セッションの永続化も無効化し、生成プロセス側に会話の記録を残さない。起動時の環境変数は必要最小限に限る。
  - 除去できない情報（日付・OS等の環境情報、アカウント情報が含まれるかどうかを含む）は、フェーズ1で実際に何が渡るかを確認し、キャラ生成への影響が許容範囲であることを確かめる。
- Muse 本体（エージェント）の役割は仲介の監督と例外対応（取り込み、失敗時の案内）に限る。
- 実測確認済み（2026-11-23）: テスト用キャラの設定だけを渡した独立プロセスの返信は、テスト用キャラの一人称・口調のみで混入は見られなかった。ただし1例のみのため、品質確認は9章の基準で改めて行う。

### 3.1 1対1の生成材料
- システムプロンプト: 共通ルール（本アプリ専用。返答だけを返す、長さの目安は通常140字・最大500字、設定に無いことは捏造しない等）＋ キャラ設定文（設定本文＋関係・呼び方）。
- ユーザープロンプト: 「履歴」と「対象の未返信群」を分けて渡す。対象は、リクエストの upto_seq までの未返信群全部。履歴は、対象の未返信群と、それより後の利用者の発言（まだ対象に含まれない発言）を除いた直近20発言（利用者とキャラの発言を時系列で。処理中に付いた返信も含む）。再試行時も同じ規則で材料を作る。
- 出力: 返答文のみ。

### 3.2 グループの生成材料
- システムプロンプト: 共通ルール（掛け合い用。下記）＋ 参加全員の設定本文（誰の設定か分かる見出し付き）。設定文のうち「対話相手との関係・呼び方」はグループでは渡さない（変換時に分離して保存する。3章・7章）。
- 掛け合い用の共通ルール: 各行は「表示名：セリフ」の形式で出す。発言数は6〜12。利用者は話題の提供者であり登場人物ではない（利用者へ話しかけない、利用者との関係・呼び方は適用しない）。キャラ同士の関係は、設定に無い場合は初対面として振る舞い、捏造しない。
- 出力の表示名は、プロンプト内で指定した表示名リストの表記と完全一致させる。表示名はグループ内で一意（7章）。
- ユーザープロンプト: 1対1と同じ規則。対象は、リクエストの upto_seq までの未返信プロンプト全部（複数ある場合は全部を対象とし、掛け合いはその全てを受けて生成する）。履歴は、対象のプロンプト群と、それより後の利用者の発言を除いた直近20発言。
- 出力: 「表示名：セリフ」の行の並び。受け取り側でキャラごとに分割して保存・表示する（分割規則は8章）。

## 4. 機能

### 4.1 キャラクター管理
- キャラの一覧表示（画像＋名前）と選択。
- 初期取り込み: アバターテンプレ管理アプリの現在のプロファイルを一括で取り込む。取得は同アプリのアクション経由（プロファイル書き出し＋画像取得）で行い、取得できない場合は1件ずつの書き出しJSONで代替する（フェーズ2の冒頭で取得方法を確認する）。
- キャラの追加（後から）: 書き出しJSON（avatar-profile形式）を経由して追加できる。利用者が JSON を Muse に渡し、Muse が画像の取り込みと登録を行う。画像は期限切れ対策として、アプリ側へ実体（縮小・圧縮済み）を保存する。JSON が形式不正の場合は取り込みを中断し、理由をチャットで利用者へ伝える。
- 再取り込み: 同じプロファイルIDの再取り込みは、設定文と画像を上書きし、会話履歴は保持する。プロファイルIDを持たないJSONは新規として扱い、名前が重なる場合はその旨を表示する。
- キャラの削除: そのキャラの1対1の会話ログも一緒に削除する。参加中のグループからは除外され、そのキャラの過去の発言は表示名を残して保持される。参加が2人未満になったグループは解散状態とし、新しい生成はできなくなる（ログの閲覧は可能）。削除の可否と pending の扱いは8章の状態規則に従う。いずれも確認を挟む。
- 画像の差し替えはアプリ内で行える（1.4で変更）: キャラの画像変更画面で画像ファイルを取り込み、正方形にトリミング（ドラッグで位置調整、スライダー等で拡大縮小）して保存すると、一覧・チャットの表示に即時反映される。保存する画像はトリミング後のものを縮小・圧縮した実体とする。Muse への依頼による差し替えも引き続き可能。
- キャラごとに会話履歴は分離する。

### 4.2 チャット（1対1）
- スマートフォン向けのチャット画面: キャラ画像、吹き出し形式の履歴、入力欄、送信ボタン。「返信をもらう」ボタンは置かない（1.4で廃止）。
- 発言を送信すると自動で返信生成が始まる。生成中・返信待ちの間も追加の発言は可能で、生成開始前の発言は1つのリクエストに統合され、生成中の発言は次のリクエストの対象になる。
- 履歴はキャラごとにアプリへ保存し、ログとして残す。履歴のクリア機能を持つ（確認を挟む。可否と pending の扱いは8章の状態規則に従う）。
- 返信待ち・処理中・失敗の状態と、返信待ちの経過時間が分かる表示をする。失敗時は、対象だった発言の本文が入力欄に戻り（戻し下書き、2章・7章）、失敗した旨が表示される。
- 開いている間の画面更新は定期的な再読み込み（間隔は実装時に確定。目安10秒）で行い、返信が付いたら反映される。

### 4.3 グループチャット
- 複数のキャラ（2人以上、最大5人）を選んでグループを作成・削除できる。グループごとに会話ログを持つ。
- 利用者がプロンプト（話題や指示）を投稿すると、自動でキャラ同士の掛け合いの生成が始まる（1.4。ボタンは置かない）。新しいプロンプトなしの生成はできない（プロンプト必須）。失敗時は1対1と同様に、プロンプト本文が入力欄に戻る。
- 生成結果はキャラごとに分割し、各キャラの画像・名前付きで表示する。返信待ち・処理中・失敗の状態表示と、履歴のクリア機能は1対1と同様に持つ。

### 4.4 レビュー機能（1.5で追加）
- 目的: 利用者が特定の返答について「キャラ設定と異なっている点」を指摘し、AIがキャラ設定を見直すことで、キャラの再現精度を継続的に高める。
- 入口と見た目: レビューは頻繁に使う機能ではないため、通常の会話画面の見た目を変えない。1対1画面とグループ画面に、低コントラストで小さな「レビューモード」ボタンを常設し、押すとレビューモードに切り替わる（もう一度押すと通常モードに戻る）。
- レビューモード中の操作: キャラの発言（1対1のキャラ発言、グループのキャラ発言）をタップで選択できる。選択すると指摘の入力欄と送信ボタンが現れる。指摘は自由記述（必須）。送信でレビューが登録され、処理待ちになる。
- 見直しの処理: 返信生成と同じ仲介の仕組み（独立した Claude Code プロセス）で行う。処理の開始は signalall の走査対象にレビューを含める（2分間隔の定期実行に乗り、本番でも確実に処理される）。材料は、対象キャラの現在の設定JSON（アプリが保持する元の書き出しJSON）、そのキャラの過去のレビュー履歴（指摘と差分の要約）、対象発言の本文と前後の会話数件、今回の指摘。出力は修正後の設定JSON全文（avatar-profile v1.0 形式、プロファイルIDは元のものを維持）。
- 検証と適用: 出力がJSONとして解釈でき、形式が avatar-profile で、名前が対象キャラと一致する場合のみ有効とする。変更前と変更後のJSONを項目単位で比較して差分を作る。差分がある場合は**自動で適用**する（キャラの保持JSONを差し替え、設定本文・関係を再変換して保存する。再取り込みと同じ経路で、会話履歴は保持する）。差分が無い場合は「変更なし」として記録し、適用しない。検証に失敗した場合は失敗として記録し、設定は変更しない。
- 履歴: レビュー履歴はレビューモード内の導線から、キャラごとに時系列で閲覧できる。各記録には、対象発言の抜粋、指摘、状態（処理中／完了／変更なし／失敗）、見直しの差分（項目パスごとに変更前→変更後）、再出力されたJSON全文（表示・コピー可能）を持つ。
- 取り消し: 適用済みの改訂には「取り消し」を用意し、押すとその改訂の変更前JSONでキャラ設定を上書きして戻す（戻したことも履歴に残す）。複数の改訂が重なっている場合も、取り消しは「その改訂の変更前JSONへの上書き」として単純に扱う。
- レビューの処理も生成の利用枠を消費する。処理は1件ずつ直列に行う。

### 4.5 未読の表示（1.5で追加）
- 目的: キャラの返信が届いたことに利用者が気付けるようにする。
- 未読の定義: 会話（1対1・グループ）ごとに、利用者が最後にその会話を開いてから到着したキャラ発言の数。利用者の発言やプロンプトは数えない。
- 表示: ホームのキャラ一覧・グループ一覧で、未読がある会話には件数のバッジを表示し、あわせてその行の上に赤い線を引いて新着を目立たせる。
- 既読化: その会話の画面を開くと未読は0になり、バッジと赤線は消える。会話画面を開いている間に到着した返信は、画面の状態取得をもって既読化されるため未読には数えない（開いたまま返信を待っている場合にバッジが残らないようにする）。仲介用の取得では既読化しない。

### 4.6 一覧の並び替えと簡易表示（1.6で追加）
- ホームのキャラ一覧に並び替えを付ける。選択肢は次の3つとし、選んだ並びは保持する（次回開いた時も同じ並び）。
  - 五十音順: 表示名の日本語照合順（Intl.Collator の ja 照合）。
  - 追加順: キャラの登録順（character_id 昇順）。
  - 最近使用した順: そのキャラとの会話で最後に発言（利用者・キャラを問わない）があった時刻の新しい順。会話がまだ無いキャラは末尾に登録順で並べる。
- ホームのキャラ一覧に「簡易表示」の切り替えを付ける。簡易表示では各キャラが1行（小さいアイコン＋名前。未読バッジは簡易表示でも出す）で表示される。切り替え状態は保持する。グループ一覧には適用しない。
- 不具合修正（1.6）:
  - 画像トリミングのプレビュー: ドラッグで最初の表示領域の外へ動かすと、その部分の画像が描画されず空白になる（保存自体はできる）。プレビューでは画像全体が正しく描画され、切り取り範囲のどこへドラッグしても画像が見えるようにする。保存される切り取り範囲とプレビューの対応は従来通り一致させる。
  - 未読バッジの即時消去: 会話画面を開いて既読化した後、ホームの一覧へ戻った時点でバッジと赤線が消えていなければならない（手動の更新を待たない）。一覧へ戻るたびに最新の状態を取り直す等で、一覧表示が常に最新の未読状態を反映するようにする。

### 4.7 キャラの設定ボタンとメニュー（1.7で追加）
- キャラ一覧の各キャラに、小さい「設定」ボタンを置く。一覧にあった従来の「画像を変更」ボタンは外し、設定ボタンに集約する（チャット画面ヘッダーの導線は従来通り残す）。将来的な拡張に備え、設定ボタンは各種メニューを開く入口とする。
- 設定ボタンを押すとメニューを開き、次の3項目を選べる。
  - キャラ設定閲覧: そのキャラの設定内容（設定本文と、保持している関係・呼び方など設定一式）を読み取り専用で表示する。編集はしない。
  - 画像変更: 従来の画像変更フロー（取り込み→トリミング→保存）を起動する。
  - キャラの表示名変更: 新しい表示名を入力して保存する。表示名はアプリ全体で一意でなければならず、重複する場合はエラーを表示して変更しない。変更後の表示名は一覧・チャット画面など今後の表示に反映する。過去の発言に記録済みの表示名（グループ発言の話者名など）は従来通り保持し、遡って変えない。

### 4.8 並び替えの即時反映（1.8で追加）
- 不具合: 並び替えの保持は手動更新（リロード）すると反映されるが、「並び替え方法を選択 → チャット画面へ遷移 → 一覧へ戻る」とした時に更新されていないことがある。
- 修正: 並び替え方法を選んだ時点でアプリ側へ保存し（savelistprefs を選んだ直後に呼ぶ等）、一覧へ戻った時に手動更新なしで即時にその並び順で表示されるようにする。一覧へ戻るたびに最新の状態を取り直す等で、一覧表示が常に最新の並び順を反映するようにする。簡易表示の保持など既存の保持項目の扱いも合わせて壊さない。

### 4.9 チャット画面内の「新着」区切り表示（1.8で追加）
- 目的: 新着があるチャットを開いた時、チャット画面の中で、まだ見ていなかった部分の境目を分かりやすくする（LINE風）。
- 表示: 未読の先頭メッセージの直前に、赤い線を引いて区切る。赤線の真ん中に「新着」と書く。LINEのような見た目にする。
- 区切りの位置: 開く直時点での未読の先頭メッセージの直前。対象は1対1チャットとグループチャットの両方。
- 既読化の扱い: 一覧側の既存の未読バッジ・赤線の挙動（開けば消える）は今まで通り維持する。区切りは「開いた時点の未読の先頭」を基準に一度だけ決め、開いている間に到着した返信で区切り位置が動かないようにする。

### 4.10 グループチャット選択への並び替え適用（1.8で追加）
- 不具合: グループチャット作成時のキャラ選択画面で、現在の並び替え設定が適用されていないことがある。
- 修正: 一覧と同じ並び替え（五十音順／追加順／最近使用した順の現在選択中）が、グループのキャラ選択にも常時・即時に適用されるように揃える。並び替え設定を変更した直後のグループ作成でも、変更後の並びが反映されること。

### 4.11 キャラのカテゴリ分類（1.8で追加）
- カテゴリの管理: カテゴリの登録メニューを、アプリの全般的な場所（キャラ一覧側の全体メニュー等、個別キャラ画面ではない所）に置き、そこでカテゴリの追加と削除ができるようにする。
- キャラへの分類: 各キャラは、登録済みカテゴリの中から選んで分類できるようにする（キャラの設定メニュー等から選択）。前提として1キャラに1カテゴリとする。未分類も選べる（カテゴリ無し）。
- カテゴリの削除: カテゴリを削除したら、そのカテゴリが付いていたキャラは未分類に戻す。
- 一覧での絞り込み: キャラ一覧でカテゴリを選択すると、そのカテゴリのキャラだけを表示する。同じカテゴリ同士はまとまって表示される（絞り込み中は選択カテゴリのキャラのみ表示されるため、並び順は選択中の並び替えに従う）。カテゴリを選択していなければ全キャラを表示する（今まで通り）。
- 併用: カテゴリの絞り込みは、並び替え・簡易表示と併用でき、グループチャットのキャラ選択にも同じ絞り込み／並びが効く形が望ましいが、最低限キャラ一覧で確実に効くこと。
- データ: categories（id、名前、作成日時）と、characters への category_id（未分類は空）を追加する。カテゴリ名は重複しないものとする。カテゴリ削除時は対象キャラの category_id を空に戻す（キャラ自体は消さない）。

### 4.12 チャット全文出力（コピーペースト用）（1.8で追加）
- 目的: 各チャット（1対1・グループ両方）の内容を全文、コピーペーストしやすいプレーンテキストで取り出せるようにする。
- 入口: チャット画面内のメニュー等から押せるようにする。
- 出力形式: そのチャットの全メッセージを時系列順に、次の形のプレーンテキストに整形して表示する。
  キャラ名A:会話1
  キャラ名B:会話2
  （以下同様に続く）
- 発言者名は各メッセージの発言者（キャラはそのキャラの表示名、ユーザーの発言はアプリ上でのユーザーの表示名）を使い、「発言者名:内容」の形で1メッセージごとに並べる。グループでは各発言の話者名（記録済みの表示名）を使う。分割できなかった raw 出力も、そのまま1行（または原文のまま）として含める。
- 表示はコピーペーストしやすい形にし、全文をそのままコピーできるようにする（コピーボタンの併設が望ましい）。
- 出力対象はそのチャットの全履歴であり、一部抜粋や要約にしない。

### 4.13 カテゴリのフォルダ表示（1.9で追加、4.11の表示方式の変更）
- 共有: 1つのカテゴリは複数のキャラに設定できる（複数キャラが同じカテゴリに属する）。1キャラに付くカテゴリは引き続き1つまでとする。
- 目的: 同じカテゴリのキャラ同士を同じ場所にまとめ、一覧をフォルダのように整理すること。
- 表示: キャラ一覧では、カテゴリごとにグループ化して表示する。カテゴリ名を見出し（フォルダ）として表示し、その下にそのカテゴリに入っているキャラが並ぶ。
- 開閉: カテゴリ名をクリックすると、そのカテゴリのキャラの表示／非表示が切り替わる（開閉）。開閉状態は一覧の表示に即時反映される。
- 未分類のキャラは、カテゴリのグループの外（未分類として）従来通り表示する。
- 既存のカテゴリ絞り込み（4.11）や並び替え・簡易表示との併用で既存機能を壊さない。グループ内のキャラの並びは選択中の並び替えに従う。

### 4.14 カテゴリ分けチェックボックス（1.10で追加）
- キャラ一覧に「カテゴリ分け」のチェックボックスを用意する。
- オン: 現在のフォルダ分け表示（4.13）。カテゴリ見出しの下にキャラが並び、見出しクリックで開閉する。
- オフ: カテゴリを無視した従来の全表示。カテゴリ見出しは出さず、全キャラを選択中の並び替え順でそのまま並べる。
- チェックの状態は、並び替え・簡易表示と同様に保持され、画面遷移しても戻らないことが望ましい。

## 5. 含めない物（配信関連は一切入れない）

- わんコメ連携、コメントの取り込み・検知、OBS表示、表示キューやタイプライター等の表示制御。
- 感情タグと感情アニメーション。
- コメント者プロフィール・信頼度・評価の仕組み。
- 影響システム（会話による設定の取り入れ）。キャラ設定は常に固定。
- 読み上げ（VOICEVOX・音声合成とも）。
- 配信者／通常の相手の区別、個人情報マスキング等の表示前検査。
- 利用者のPC側のプログラム（ブリッジや常駐プログラム）。※Muse の環境（VM）側の処理は2章の通り対象外とする。

## 6. 画面構成

1. キャラ選択画面（一覧、キャラ削除、画像変更への導線、グループ一覧・作成への導線）。
2. チャット画面（1対1。履歴、入力、履歴クリア、状態表示）。
3. グループチャット画面（参加キャラ表示、ログ、プロンプト入力、状態表示、履歴クリア）。
4. 画像変更画面（画像の取り込み、正方形トリミング、保存）。キャラ選択画面またはチャット画面から遷移する。

## 7. データモデル（案）

- characters: id、名前、表示名（アプリ全体で一意。正規化した表記でも重ならないよう、重複する場合は連番等で一意化する）、設定本文、関係・呼び方（設定本文と分離して保持）、元の書き出しJSON（再変換・突合のため）、画像（実体）、取り込み元プロファイルID、作成日時。
- messages: id、character_id、発言者（user / character）、本文、日時、seq（キャラ内の連番。並び順の保証に使う）、request_id（キャラの返信のみ。どのリクエストへの返信か）。
- groups: id、名前、参加キャラID（複数）、状態（active / dissolved)、作成日時。
- group_messages: id、group_id、種別（user / character / raw）、character_id（character の時のみ）、speaker_name（表示名。キャラ削除後も表示を保つため発言側に保持）、本文、日時、seq（グループ内の連番）、request_id、split_status（通常 / 分割異常）。
- reply_requests: id、対象種別（chat / group）、対象ID、upto_seq（対象とする最終発言の seq。これより後の発言は次回の対象）、状態（pending / processing / done / failed / cancelled）、失敗理由（timeout / generation_error / rate_limited 等）、作成・開始・完了日時。
- 戻し下書き（1.4で追加）: 対象ごとに最大1件。本文（失敗したリクエストの対象だった利用者発言を、時系列順に改行で連結したもの）と、失敗理由・失敗日時を持つ。リクエストが failed に確定した時点で作成され、対象の利用者発言はログから削除される（seq は再利用しないため欠番になる）。画面は下書きがあれば入力欄へ復元し、新しい発言が投稿された時点で下書きは消去される。
- reviews（1.5で追加）: id、character_id、対象種別（chat / group）、対象の発言ID、対象発言の本文（発言が消えても履歴が読めるよう複写を保持）、指摘本文、状態（pending / processing / done / no_change / failed）、失敗理由、作成・処理日時。
- setting_revisions（1.5で追加）: id、character_id、review_id、変更前JSON、変更後JSON、差分（項目パス・変更前・変更後の組の配列）、適用日時、取り消し日時（取り消された場合）。
- 未返信の判定規則: 対象の発言のうち、最後に done になったリクエストの upto_seq より後にある利用者の発言（群）を未返信とする。処理中に追加された発言は今回の対象に含めず、次回の対象とする。
- リクエストの規則: 同一対象で有効な（pending / processing）リクエストは1件まで。合図が重なった場合は、既存の pending の upto_seq を最新の発言まで進めて統合する（processing への統合はしない）。pending から processing への遷移は状態を条件として行う。返信の保存と done への更新は1つのアクションで実行し、request_id で冪等にする。
- 書き戻しの受理条件: 書き戻しは、そのリクエストの状態が processing の場合のみ受け付ける。failed / done / cancelled になっているリクエストへの書き戻しは破棄する（タイムアウト後に遅れて完了した生成が、再合図による新しい返信と二重に付くことを防ぐ）。
- processing の確定と復旧: 生成プロセス自体には制限時間（5分）を設け、超過したら強制終了する。開始から10分を超えた processing は、仲介が次にその対象へ触れた時（合図の処理、処理開始、状態の確認）に failed（timeout）へ確定する。pending には戻さない。failed に確定した時点で戻し下書きが作られ、利用者は入力欄に戻った文章を再送信することで再試行できる。
- seq は対象ごとに単調増加とし、再利用しない。履歴をクリアしても採番は戻さない（カウンタを対象側に保持する）。
- アプリ外（Muse の記憶や配信ツールのデータ）とは混ぜない。会話ログの正本はアプリ内のみ（生成プロセス側に会話の記録を保存しない）。

## 8. 異常系と生成結果の検査

- 生成の失敗・タイムアウト: リクエストを failed として記録し、画面に表示する。再試行は戻し下書きからの再送信による（自動リトライはしない）。生成プロセスの制限時間と processing の確定規則は7章の通り。
- 状態と操作の組み合わせ: 10分以内の processing がある対象は、履歴クリア・キャラ削除・グループ削除・グループ解散ができない。10分を超えた processing がある場合は、まず failed（timeout）に確定してから実行する（確定せずに実行すると、後から遅延書き戻しが受理されて、クリア後の履歴や削除済みの対象に返信が入り得るため）。pending がある対象は、それらを行う際にリクエストを cancelled にしてから実行する。キャラ削除の禁止条件には、そのキャラ自身の対象に加え、そのキャラが参加するグループの processing も含める。
- 利用枠の上限到達: 失敗理由 rate_limited として区別して表示する。
- 生成結果の検査: 主な判定は生成プロセスの終了コードと空の出力とし、失敗として扱う。明らかなエラー文・拒否文も補助的に判定して失敗とする（グループの場合は、拒否文を raw で保存せず失敗を優先する）。長さや発言数の目安からの逸脱は許容し、そのまま表示する。
- グループの分割規則: 行ごとに次の順で判定する。(1) 正規化したうえで、コロンより前の部分が名簿（表示名リスト）の表示名と完全一致する行は、そのキャラの新しい発言とする。半角・全角コロン、空白、装飾記号は正規化して照合する。(2) 「名前：」の形（コロン前の部分が20字以内で空白を含まない）だが名簿に無い行は、直前の発言の続きとはせず、raw として原文のまま保存する。(3) どちらの形でもない行は、直前の発言の続きとする（複数行のセリフに対応し、直前が raw の場合は raw に連結する）。直前の発言が無い場合（先頭の前置き行など）は raw として保存する。前置きは除去せず、原文を失わない。有効な行が1つも無い場合も、原文全体を raw として保存し、リクエストは done とする（分割の異常は split_status で表し、失敗理由には使わない）。raw は画面で「分割できなかった出力」として原文表示し、次回以降の履歴には話者不明のテキストとして含める。
- JSON の形式不正: 取り込みを中断し、理由を利用者へ伝える。登録済みデータには影響させない。
- 画像の取得失敗: 画像なしで登録し、その旨を利用者へ伝える（差し替えは Muse への依頼で可能）。
- 同時合図・処理中の操作: リクエストの状態管理で二重生成を防ぐ。処理中の対象は、履歴クリアとキャラ削除を不可とする。

## 9. 受け入れ基準

- スマートフォンでキャラを選んで発言でき、ボタンの追加操作なしに、そのキャラらしい返信が表示されること。
- 生成失敗時に、失敗であることと理由が画面で分かり、対象の発言が入力欄に戻って再送信できること。
- キャラ画像をアプリ内で取り込み・トリミング・保存でき、表示に反映されること。
- レビューモードでキャラの発言を選んで指摘を送ると、見直しが処理され、差分が履歴に残り、設定が自動で更新されること。不正な見直し結果では設定が変わらないこと。適用済みの改訂を取り消して設定を戻せること。通常モードの見た目にレビュー機能が目立たないこと。
- 混入チェック: 対象3キャラ以上で各3回以上生成し、一人称・語尾・呼び方・禁止要素（Muse 本体のペルソナの要素）のチェックリストで確認する。最終判定は利用者が行う。長い履歴（20発言超）の状態でも1回試す。
- グループの混同チェック: 一人称や口調が近い組、遠い組、人数の多い組で各2回以上試し、一人称・呼び方の取り違えがないか確認する。最終判定は利用者が行う。
- 会話ログがアプリ再訪後も残っていること。キャラごとに分離されていること。
- JSON 経由でキャラを追加でき、再取り込みで履歴を保ったまま設定を更新できること。
- グループでプロンプトを投稿し、合図後に掛け合いがキャラごとに分かれて表示されること。分割の崩れ例（前置き、名簿外の名前、表記揺れ）でも原文が失われないこと。
- 配信関連の機能・文言が、アプリの画面と共通ルール内に存在しないこと（キャラ設定文そのものに含まれる記述はキャラ設定として扱い、対象外とする）。
- 生成失敗時に、失敗であることと理由が画面で分かること。
- 制限の明記: 生成に渡す履歴は直近20発言までで、それより前の会話は参照されない。この制限は利用者への案内に明記する。会話ログの外部への書き出し（バックアップ）は初版では用意しない（アプリを削除するとログも消える旨を案内する）。

## 10. 数値の初期値

- 生成に渡す履歴: 直近20発言。未返信群は全部。
- 返答の長さの目安: 通常140字、最大500字。
- グループの発言数: 6〜12発言。参加人数: 2〜5人。
- processing のタイムアウト: 10分。生成プロセスの制限時間: 5分（超過したら強制終了）。
- 生成モデル: Claude Code の既定（連携アカウントの既定モデルに委ね、特定モデルへは固定しない）。
- 設定文の長さ: 変換仕様（配信ツールと同一。人物設定は4000字で切り詰め等）に準拠する。
- 画像: 縮小・圧縮済みの実体を保存する（1キャラ数百KB目安）。

## 追加仕様 v1.7（2026-11-24）: カテゴリの階層化

- カテゴリに親カテゴリ（parent_id、null=最上位）を1つ持たせる。深さは無制限。
- 絞り込み: カテゴリ X を選ぶと、X およびその子孫カテゴリ全てに割り当てられたキャラを表示する。対象はキャラ一覧の絞り込み、グループ作成の絞り込み、参加者変更の絞り込みの全て（判定は共通）。
- キャラへのカテゴリ割り当ては従来通り（複数選択）。親カテゴリへの表示は絞り込み時に子孫を辿って自動判定し、割り当ての保存は変えない。
- 表示: カテゴリを選ぶUI（絞り込みセレクト、割り当てチェックボックス一覧、カテゴリ管理一覧）では、階層を字下げした階段式（ツリー順）で並べる。
- 編集: カテゴリの作成・編集時に親カテゴリを指定・変更できる。自分自身および自分の子孫を親にすることは禁止（循環防止、サーバ側でも検証）。
- 削除: カテゴリを削除すると、その子カテゴリは削除したカテゴリの親の下へ付け替える（親が無ければ最上位）。キャラとの割り当ては削除したカテゴリ分のみ解除（従来通り）。
- 既存データ: 既存6カテゴリは全て最上位のまま移行。初期設定として「マリオ」（id 5）を「ゲーム」（id 8）の子に設定する（ユーザーの指定）。

## 追加仕様 v1.7.1（2026-11-24）: カテゴリ割り当ての親子排他

- キャラへのカテゴリ割り当てでは、子カテゴリとその祖先カテゴリ（親・祖父…）を同時に付けることはできない。両方が付く状態になったら、子（より深い方）だけが残る。
- 割り当てUI: 子カテゴリにチェックが入っている間、その祖先カテゴリは選択できない。逆に子カテゴリをチェックすると、付いていた祖先カテゴリは自動で外れる。サーバ側（setCharacterCategories）でも同じ規則で祖先側を落として保存する。
- カテゴリの親子関係を後から変更（親の設定・変更）した時も、既存の割り当てに同規則を適用し、親子で重なった割り当ては子だけに整理する。
- 既存データにも適用する（例: マリオ＋ゲーム両方付いたキャラはマリオだけになる）。絞り込み表示は子孫展開のため変わらない。

## 追加仕様 v1.8（2026-11-25）: キャラ設定の手動編集（整形フォーム）

- ユーザーがキャラの設定を自分で書き換えられるようにする。JSON生データではなく、項目ごとに整形したフォームで編集する。
- 入口: キャラの設定メニューに「設定を編集する」を追加（ユーザーの指定でこの文言。既存の「キャラ設定を見る」と同じ画面系統から入る）。
- フォーム項目: 名前、概要、背景（本文・関連リンク・つながりの要約）、話し方（一人称・口癖・話し方の説明・メモ）、相手との関係（ユーザーの呼び方等）、見た目の要素、フレーバー特性（1件ずつ編集、有効/無効の切替、追加・削除）。長い項目は複数行入力。
- 保存でキャラチャット内の設定に反映し、次の生成から使われる。アバター管理ツールの正本は触らない（レビュー機能の自動適用と同じ保存先）。
- 一覧の表示名は従来通り別設定（表示名の変更）であり、この編集では扱わない。

## 追加仕様 v1.9（2026-11-25）: グループ人数の拡張（1〜8人）

- グループの参加人数は作成・参加者変更とも **1〜8人** とする。
- 作成時だけでなく、参加者変更（updateGroupMembers）でも1人を選んで保存できるようにする（従来は変更時2〜5人必須だった制限を撤廃）。
- 返信待ち・生成中は参加者変更不可、という従来の制限は維持。
- 1人グループ＋なりきり「自分だけが演じる」でAIが書けるキャラが居ない場合は返信を生成しない、という従来の例外も維持。
- 生成側（プロンプト・分割処理）に人数の上限前提（5人）が残っていれば8人まで扱えるよう合わせる。
